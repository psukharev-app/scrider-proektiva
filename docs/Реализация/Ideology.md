# Документ 2. Идеология подхода Scrider

## 1. Функциональная парадигма вместо ООП (Parchment)

### 1.1. Основной принцип

Scrider сознательно отказывается от ООП-подхода Quill (Delta + Parchment + Editor) в пользу **функциональной парадигмы**.

**ООП (Quill / Parchment):**
- Дерево Blot-объектов (~1000 объектов на 1000 символов)
- Двойная память (Blots + DOM)
- MutationObserver для непрерывной синхронизации
- Stateful, мутабельные объекты
- Lifecycle: create → update → remove

**Функциональный подход (Scrider):**
- Delta = JSON-массив операций
- Один источник правды (Delta)
- Без MutationObserver
- Stateless processing
- Иммутабельные данные
- Нет lifecycle — только чистые функции

### 1.2. Аналогия с React

React перешел от классов к функциональным компонентам и хукам. Причина — функции простые, легковесные, композируемые. Scrider следует этой философии на уровне текстового движка.

## 2. WYSIWYG без «двух королей»

### 2.1. Проблема классических WYSIWYG

В Quill и аналогах возникает конфликт:
- **Parchment** управляет DOM через Blot-дерево
- **React** пытается управлять DOM через виртуальный DOM

Результат — два «короля одного замка», гонки, рассинхрон, сложность интеграции.

### 2.2. Решение Scrider

**Единственный менеджер DOM — браузер + React (точечно):**
- По умолчанию: браузер управляет DOM через contentEditable
- React НЕ перерисовывает innerHTML на каждый keystroke
- При форматировании (Ctrl+B, paste): React перерисовывает DOM один раз
- Нет второго «живого» дерева в памяти

---

## 3. Uncontrolled по умолчанию, Controlled по триггерам

### 3.1. Почему не pure Uncontrolled

Чистый Uncontrolled (доверить всё браузеру) ломается на:
- **Paste** — браузер вставляет произвольный HTML (Word, чат)
- **Сложной разметке** — декорации, списки, code block
- **Разном поведении браузеров** — Delete/Backspace на границах блоков

### 3.2. Почему не pure Controlled

Pure Controlled (перерисовка на каждый keystroke) даёт **«rich-lag-editor»**:
- Каждый символ → полный пересчёт + замена DOM
- На больших документах (1000+ символов) — заметные задержки

### 3.3. Решение: Combined Managed

**Uncontrolled по умолчанию** (ввод, Delete, Enter) — браузер правит DOM, мы читаем и обновляем Delta.

**Controlled по триггерам** (7 категорий: paste, форматирование, InputRules, drop и др.) — редактор перехватывает событие, нормализует, обновляет Delta, один раз перерисовывает DOM.

Это даёт:
- Скорость нативного редактора (нет перерисовки на каждый символ)
- Предсказуемость сложных операций (paste, форматирование)

## 4. Delta как единый формат для всего

### 4.1. Один формат — множество применений

Delta используется для:
- **Хранения** — JSON-документ в БД
- **Передачи** — коллаборация, AI-сервер
- **Отображения** — через `deltaToHtml()`
- **Экспорта** — PDF, DOCX, Markdown, HTML
- **Контроля версий** — diff через `diff()` и `compose()`

### 4.2. AI-native архитектура

Delta = JSON — идеальный формат для AI-обработки:
- AI сервер получает Delta → конвертирует в Markdown → отправляет в LLM
- LLM возвращает Markdown → конвертирует в Delta
- `diff()` с оригиналом → получает change Delta для клиента

**Key insight:** Processing (formatter) может работать на сервере, не требуя DOM.

## 5. Расширяемость без монолита

### 5.1. Три уровня расширения

| Уровень | Что расширяет | Лицензирование |
|---------|---------------|----------------|
| **Schema** | Форматы данных (как хранить) | Бесплатно (чтение) |
| **Plugin** | Поведение (как редактировать) | Лицензируемое |
| **Module** | UI (как создавать) | Лицензируемое |

**Принцип:** контент всегда читаем. Возможность редактировать и создавать — лицензируется.

### 5.2. Пример: code-block

- **Schema** (`code-block` format) — бесплатно. Код виден как plain text.
- **Plugin** (`prismRenderer`) — лицензия. Подсветка синтаксиса.
- **Module** (кнопка в toolbar) — лицензия. Можно создать блок.

## 6. Минимальный bundle через плагины

### 6.1. Проблема монолитных редакторов

TinyMCE, CKEditor, Quill тянут всё сразу: подсветку кода, формулы, диаграммы → 500KB+ bundle.

### 6.2. Решение Scrider

Базовый редактор (`@scrider/editor-react`) содержит только core-функциональность. Всё остальное — отдельные npm-пакеты:

```
@scrider/plugin-prism      — подсветка кода (тянет Prism.js)
@scrider/plugin-katex      — формулы (тянет KaTeX)
@scrider/plugin-mermaid    — диаграммы (тянет Mermaid)
@scrider/export            — PDF/DOCX (тянет pdfmake, docx)
```

Пользователь подключает только то, что нужно. Bundle растет пропорционально использованным функциям.

### 6.3. Lazy loading через dynamic import

```typescript
// Плагин экспорта PDF
function exportPdf(state: EditorState): CommandResult {
  return {
    state,
    sideEffect: async () => {
      const pdfMake = await import('pdfmake');  // загрузка только при клике
      // ... генерация PDF
    },
  };
}
```

## 7. Тестируемость как архитектурный принцип

### 7.1. Четыре слоя — четыре уровня тестирования

| Слой | Тестирование | Инструменты | Без DOM |
|------|--------------|-------------|---------|
| delta | Unit (316 тестов) | Vitest | ✅ |
| formatter | Unit + интеграционное (864 теста) | Vitest + jsdom | ⚠️ (опционально) |
| editor-core | Unit (417 тестов) | Vitest | ✅ |
| editor-react | Интеграционное (191 тест) | Vitest + jsdom | ❌ (требует DOM) |

### 7.2. Почему это важно

- **Core можно тестировать без браузера** — быстрые CI/CD
- **Моки не нужны** — чистые функции (input → output)
- **Серверные сервисы** (AI, collab) используют те же unit-тесты

## 8. Итог: философские принципы Scrider

1. **Один источник правды** — Delta, а не дерево DOM-объектов.
2. **Функции, а не объекты** — stateless processing, иммутабельные данные.
3. **Uncontrolled по умолчанию, Controlled по триггерам** — скорость + предсказуемость.
4. **Расширяемость через композицию** — Schema (чтение) + Plugin (редактирование) + Module (создание).
5. **Минимальный bundle** — плагины как отдельные пакеты, lazy loading.
6. **AI-native** — Delta = JSON, formatter работает на сервере.
7. **Тестируемость** — core без DOM, быстрые тесты.
8. **Framework-agnostic core** — React, Vue, Angular — одинаковый core.
